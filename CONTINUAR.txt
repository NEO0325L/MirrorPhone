LEE ESTE ARCHIVO PRIMERO
Este documento permite continuar el desarrollo en otra sesión o equipo.
El ZIP de continuación incluye las fuentes del proyecto, no una instalación
lista para ejecutar. No contiene claves, certificados, datos de emparejamiento,
node_modules, cachés, grabaciones ni el framework binario de WebRTC para iOS.

1. OBJETIVO DEL PRODUCTO

Compartir imagen y sonido del iPhone en una app ejecutable de escritorio,
actualmente dirigida a Windows 11 x64 y Linux Mint 22.x x64. El usuario quiere
un flujo sencillo: abrir el receptor, crear una sala e introducir su código
en la app iOS. No debe requerir visitar otra página ni introducir OWNER_KEY.
Debe funcionar entre redes distintas cuando la conexión directa o TURN lo
permitan. Mantener baja latencia y buena calidad sin consumo innecesario.

El control global del iPhone con teclado y ratón sigue pendiente. El usuario
quiere Wi-Fi o Internet, sin USB, sin comprar accesorios y sin una Mac como
puente. No anunciar esta función como implementada. Bluetooth se había
considerado únicamente como último recurso, no como requisito aceptado.

5. CÓMO ABRIR Y SEGUIR DESDE OTRO EQUIPO

Opción preferida: instalar Git y clonar el repositorio.

  git clone https://github.com/NEO0325L/MirrorPhone.git
  cd MirrorPhone

Opción ZIP: extraer el archivo completo y abrir la carpeta MirrorPhone.
El ZIP no incluye la carpeta .git ni conserva el historial local. Si vas a
publicar cambios, conviene clonar y copiar tus modificaciones al clon.

Desarrollo de escritorio, con Node.js 24 LTS y npm:

  cd desktop
  npm ci
  npm test
  node ../cloudflare/check-worker.mjs
  npm start

Compilar en Linux:

  npm run build:linux

Compilar en Windows:

  npm run build:windows

Resultados: desktop/dist/. No subir dist ni node_modules al historial Git.
El workflow permite ejecución manual y etiquetas v*. No publica Releases
por sí mismo. Para actualizar GitHub se necesita la sesión propia del usuario;
este ZIP no lleva acceso a su cuenta.

iOS:
- Requiere macOS, Xcode, SDK/dispositivo compatibles y firma del desarrollador.
- Usar Python 3.11 o posterior para scripts/prepare-ios.py, que utiliza
  hashlib.file_digest. El Python 3.9 de algunas instalaciones de Xcode no basta.
- Ejecutar desde la raíz: python3 scripts/prepare-ios.py.
- Abrir ios/MirrorPhone.xcodeproj, seleccionar tu equipo de firma y un bundle
  identifier único. La copia pública no contiene el equipo de firma original.
- No cambiar la identidad de una app ya instalada sin considerar que puede
  instalarse como una aplicación distinta y perder su configuración anterior.

6. CORRECCIONES DE AUDIO/VÍDEO QUE NO DEBEN PERDERSE

Audio:
- En Electron, conectar solo WebAudio no iniciaba siempre la decodificación
  WebRTC. MirrorAudioPlayer mantiene un elemento de audio auxiliar SILENCIADO
  con autoplay/srcObject/play para impulsar el decodificador.
- La única salida audible sigue siendo Web Audio a 48 kHz; evitar rutas
  duplicadas, eco o dos relojes independientes.
- Mantener activación por gesto del usuario, ganancia, limpieza de conexiones
  y cancelación de reanudaciones tardías al desconectar.
- CaptureAudioDevice.swift debe consumir los ticks acumulados del temporizador
  Dispatch, con el límite existente; ignorarlos provocaba audio robótico.
- Un episodio anterior de audio ausente fue causado por el silencio del sistema
  macOS. Comprobar salida/volumen antes de atribuirlo al transporte. No forzar
  el volumen del sistema desde el producto.

Vídeo:
- Mantener H264HardwareProbe.swift y ScreenEncoderFactory.swift. Las pantallas
  verticales 1080x2336 requieren un nivel H.264 superior al predeterminado.
- El receptor consulta VideoDecoder.isConfigSupported antes de ajustar el
  nivel H.264 de la respuesta SDP; preservar perfil, audio, RTX y las condiciones
  de negociación asimétrica. Eliminar esa corrección llegó a dejar audio sin vídeo.
- ScreenQualityController.swift adapta resolución/FPS según bitrate y QP.
  La selección 1080p/60 FPS son máximos, no promesas de frecuencia constante.
- Evitar colas adicionales que acumulen frames y aumenten el retraso.
- No prometer latencia cero. Distinguir RTT, búfer y retraso extremo a extremo.

7. SEGURIDAD Y ALOJAMIENTO

- Flujo actual por código de sala; la autorización OWNER_KEY es heredada.
- Cloudflare Worker + D1 almacenan señalización temporal, no grabaciones.
- TURN se obtiene del servicio Hugging Face/FastRTC; la clave del proveedor
  debe permanecer como secreto del servidor, nunca dentro de las apps.
- Secretos existentes del despliegue: SESSION_SECRET, HF_TOKEN y posiblemente
  OWNER_KEY heredado. Este documento solo enumera sus nombres, no sus valores.
- No pedir al usuario que pegue claves en el chat ni leerlas para incluirlas
  en repositorios, capturas, logs o paquetes.
- Los servicios externos tienen cuotas y disponibilidad propias. El usuario
  no quiere cobros; no activar planes de pago ni prometer uso gratuito ilimitado.
- Mantener sandbox de Electron, aislamiento de contexto y Node desactivado
  en el renderizador. No usar --no-sandbox como solución de instalación.
- Linux: no persistir credenciales con el backend safeStorage basic_text.
- Conservar .gitignore y .gitattributes; no añadir cachés, perfiles de firma,
  datos de confianza del teléfono ni contenido personal.

8. TECLADO Y RATÓN: ESTADO EXPERIMENTAL

El kit experimental/control-wifi usa pymobiledevice3 11.33.1. Permite preparar
el entorno Windows, emparejar por Wi-Fi y comprobar servicios de desarrollo.
Sus acciones actuales son pair, check y prepare: NO envían clics ni teclas.
Se había comprobado en Mac acceso de solo lectura a servicios HID del iPhone;
no se demostró control completo desde Windows ni a través de Internet.
Las APIs normales de una app iOS no conceden control global de otras apps.
No confundir transmisión de pantalla con permiso para inyectar entradas.
